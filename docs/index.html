Consequence, stated plainly. The training labels in the data tab are the existing USGS Quaternary compilation, but both prize phases score the expert-mapped new fault dataset. A submission that reproduces the catalogue earns credit only where the experts' new labels coincide with it, and every DTI printed elsewhere on this site is a monitor against the wrong population. That asymmetry is also why the emission width was measured rather than assumed: the adopted policy is a thinned skeleton (width 0 px) at floor 0.1 — at that floor the measured width curve peaks at 0 px on every ensemble, so a wider band would lower the score, not raise it — see the width measurement.

The task

Predict where geological faults are in the GeoDAWN region of northwestern Nevada — faults being surface indicators of geothermal resources. The submission is a single-band float32 GeoTIFF of per-pixel probabilities on the competition grid (submission format).

The twist that shapes everything: the public USGS fault database is incomplete. Scoring uses a private set of newly-expert-labelled faults absent from that database, and after the initial round an expert panel reviews every team's predictions to expand the label set for a final re-scoring (competition structure). Predicting the known faults back is therefore not the goal; finding the unmapped ones is.

Key findings so far

  1. The feature stack has 19 bands, not the 10 implied by the problem page's prose. All 19 carry band_name/data_category tags. Full list on the Data page.
  2. example_submission.tif is not "total fault absence". It is bit-identical to the label raster (60,988 positive pixels in both). The problem page describes it as predicting total absence. Flagged as an irregularity — see Data.
  3. The metric rewards precision, not generosity. Despite β/α = 4 nominally punishing misses, predicting everything scores 0.096 while predicting a precise quarter of the faults scores 0.554. See Metric for the algebra and the measured table.
  4. The DEM link PDF has no text layer. It is a scan; three text extractors return zero URLs. Recovered by OCR and then re-confirmed tile-by-tile against the live USGS bucket.
  5. A whole ensemble run was reported green while producing no submission at all. The blend crashed on a TIFF tile-size rule, the crash was masked by a missing pipefail, and a 110-byte stub was committed as submission.tif. Found by auditing the committed artifacts on 2026-09-16 and fixed; see Results.
  6. Both prize phases score new faults only. Verbatim from the official rules (§1.1, §3.3, §3.5): the training labels are the existing catalogue, the labelled test data are faults missing from it. The catalogue DTI quoted everywhere is a plumbing monitor, not a leaderboard proxy — Metric quotes the sentences.

The bar, from the competition itself: the best public leaderboard score is 0.2854 DW-Tversky (50 ranked entrants, median 0.1134), read from the leaderboard at 2026-09-21T04:09:25+00:00. This repository is not on it yet — see Verification.

Where this stands

2026-09-17 (session 10): the ensemble that was supposed to answer the width question had already lost six fully-trained folds. Run 35170395055 — the queued second ensemble, fired in session 9 — trained all six folds for ~3 hours and then staged nothing: the workflow told the trainer mc_id = matrix.fold (0…5) while the staging step looked for heldout_mc(FOLD_OFFSET + fold).npz (6…11), so cp failed on every fold, the artifact upload was skipped, and the blend job correctly refused an incomplete fold set. The failure record could not be committed either, because the blend job's Checkout had been skipped and the evidence step ran without a .git directory. The fold identity now reaches the trainer, staging globs whatever the trainer wrote and asserts the manifest's fold id, uploads run even when staging fails, and tests/test_ensemble_workflow.py executes the workflow's own shell against planted artefacts (re-introducing either defect fails 4 tests). The second ensemble has been re-fired on the fixed workflow.

The width question got a direct measurement, and the answer is uncomfortable. Instead of sweeping floors on the probability map, scripts/measure_miss_distance.py takes the shipped submission, grows its emitted pixels by k and scores with the official metric against the USGS faults the training labels do not contain. The median unseen-fault pixel sits 22 px = 2.2 km from anything the model emitted, only 4.9% of that truth is inside the metric's own 300 m tolerance, and widening the band to 16 px lifts the score from 0.0247 to 0.0713 — the first measured policy here that beats the constant-ones baseline (0.0585). 74% of the truth has nothing emitted within 1.2 km, so the model's detection, not the band width, is the binding constraint. See Metric for the curve and the projection against the hidden scored-truth size; the default still waits for the second ensemble to reproduce the gain.
